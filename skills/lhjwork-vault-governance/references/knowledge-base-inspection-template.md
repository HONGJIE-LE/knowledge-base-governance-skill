# 模块一：通用知识库检查模板

本模板由已复核的知识管理教程修订版 12 提炼，并改写为可用于不同 Obsidian、MOMA 或本地 Markdown 知识库的通用检查方法。

模板中的“入口、采集、知识、项目、判断、成果”等词只表示功能，不是规定的目录名、标签名或属性名。检查时先识别知识库现有板块可能承担的功能，再评价功能是否清楚、有效和可持续；不得先套模板标签，再要求知识库迁就标签。

## 一、检查原则

1. 目录名不同不算问题，功能缺失、定位冲突、无法找到或无法使用才算问题。
2. 先看实际内容、链接、属性、活动和使用痕迹，再判断板块功能；目录名称只能作为弱线索。
3. 同一个目录或文件可以同时承担多个功能，例如会议记录既是来源材料，也可能是项目证据和判断修正记录。
4. 一个功能可以分散在多个板块，只要入口清楚、关系稳定、人工和 AI 都能找到，就不强求合并。
5. 不要求知识库具备 Raw、Wiki、Projects、Outputs、GAP 或任何指定标签；这些词只可作为内部分析视角。
6. 优先检查真实使用效果：能否找到、理解、关联、行动、输出和复盘。
7. 不把文件数量、属性数量或链接数量直接当作质量结论。
8. 没有打开正文，只能写“扫描到候选”，不能评价内容质量。

## 二、先识别功能板块

检查前先建立“功能候选图”，从全部一级目录、主要入口、近期活跃文件和代表性样本中识别下列功能。并非每个知识库都必须具备全部功能。

| 可能的功能 | 要解决的问题 | 常见线索，不是硬性名称 |
|---|---|---|
| 入口与导航 | 从哪里开始，当前重点是什么 | START、首页、工作台、README、地图、索引 |
| 用户或岗位上下文 | 知识库服务谁、负责什么 | 关于我、职责、主线、目标、团队 |
| 采集与来源 | 原件、外部资料、新输入放在哪里 | 收件箱、附件、剪藏、会议、参考、来源 |
| 提炼知识 | 材料如何变成可复用理解 | 主题、概念、说明、知识、研究、Wiki |
| 项目与行动 | 进行中的事情如何推进 | 项目、任务、现场、计划、行动、待办 |
| 判断与复盘 | 为什么这样判断，结果如何修正 | 判断、决策、复盘、假设、验证、经验 |
| 人物与组织 | 关键对象和关系如何保存 | 人物、客户、机构、组织、联系人 |
| 成果与交付 | 可复用或对外成果如何找到 | 输出、交付、报告、方案、成品、发布 |
| 方法与模板 | 重复工作如何标准化 | 方法、流程、模板、SOP、规范、技能 |
| 归档与参考 | 历史内容如何保留但不干扰当前工作 | 归档、历史、参考、Archive |
| 系统与自动化 | 工具配置、插件和脚本如何支撑使用 | `.obsidian`、`.moma`、脚本、配置、自动化 |

每个候选映射必须记录：

- 实际路径或文件名；
- 可能承担的功能，可多选；
- 判断依据：正文、链接、属性、活动或入口引用；
- 置信度：高、中、低；
- 是否需要继续抽样或由用户确认。

目录名与正文用途冲突时，以正文和真实使用关系为准。无法确认时写“功能待确认”，不得强行归类。

## 三、采集与来源

- 新材料是否有低摩擦入口，还是散落在多个位置无人处理。
- 原始文件、网页、截图、会议记录、AI 稿和外部链接是否保留来源。
- AI 摘要是否仍能回到原件，是否被误写成原始事实。
- 新输入是否有处理状态或等价的处理痕迹。
- 外部参考是否与用户自己的观点、判断和成果保持边界。
- 长期未处理内容是否影响检索和当前工作。

不要因为没有“Raw”目录就判定采集缺失。必须先找功能等价的收件箱、附件区、会议区、来源索引或其他入口。

## 四、提炼与关联

- 材料是否形成摘要、主题说明、项目背景、人物说明、方法或其他可复用内容。
- 新内容是否优先关联已有页面，避免重复主题和同义页面。
- 索引、目录页、双链、反向链接或其他导航是否能让人工和 AI 找到上下文。
- 事实、用户原话、外部观点、AI 推断和确认结论是否区分。
- 新旧信息冲突时是否保留来源和变化，而不是直接覆盖。
- 标签是否少而稳定；关系是否主要依靠正文、链接和结构表达。

不要因为没有“Wiki”目录就判定没有知识层。主题笔记、项目背景、研究文档、说明页或长期维护文档都可能承担知识提炼功能。

## 五、项目与行动

- 真实在推进的事项是否有稳定入口或功能等价的控制页。
- 是否能找到目标、相关材料、当前判断、进度、负责人和下一步。
- 下一步是否具体、可执行，而不是长期口号。
- 项目之间是否被一个大目录混在一起，导致状态和责任不清。
- 会议、任务工具或外部系统中的行动是否能回到知识库上下文。

不要因为没有“Projects”目录就判定项目管理缺失。专题页、客户页、案件页、任务清单或工作台都可能承担项目现场功能。

## 六、判断与复盘

- 是否保存“判断是什么、为什么、依据什么、目前是否验证”。
- 是否能区分事实、假设、候选判断和已确认结论。
- 行动结果是否回写，并留下修正、推翻或继续坚持的原因。
- 面对新问题时，能否找到过去相似判断和结果。
- 复盘是否改变下一次行动，而不是只记录过程。

判断可以集中在索引、项目页、会议记录或复盘中，不要求单独建立“判断”目录。功能存在且可调用即可。

## 七、成果与再利用

- 成果是否有稳定入口，能回到相关来源、项目和判断。
- 当前版本、历史版本和正式版本是否能区分。
- 对外文件、内部底稿和过程稿是否保持边界。
- 成果完成后是否回写项目状态、经验和下一步。
- 后续任务是否能复用已有成果，而不是重新开始。

不要因为没有“Outputs”目录就判定成果管理缺失。成果可以保留在原位置，通过索引、链接、发布页或项目入口统一调用。

## 八、基础技术能力

- Markdown 标题、列表、表格、引用和代码块是否便于人工与 AI 读取。
- 内部链接、标题链接、附件链接和反向链接是否可用。
- 是否存在大量孤立页、重复目标、同名冲突或无效链接。
- 图片、PDF、Word、Excel、音视频等附件是否有稳定落点和来源说明。
- 开发目录、缓存、构建产物是否干扰搜索、图谱和性能。
- 应用未运行时，只报告文件层结果，不声称验证了渲染或插件运行。

## 九、属性、查询与自动化

- 先识别知识库正在使用的属性体系，再检查同一字段是否混用多种含义。
- 不强制套用某套固定属性；仓库已有明确规范时，以其规范为准。
- Dataview、Bases 或其他查询是否服务真实管理动作，而不是只做展示。
- 查询结果是否能追溯到来源文件，是否存在空字段、重复行或过期条件。
- 模板是否减少重复输入，而不是增加填写负担。
- 自动移动、自动改状态、自动登记或自动删除是否具备确认和恢复机制。

## 十、插件、同步与安全

- 区分“已安装”“已启用”“运行正常”。
- 插件是否对应真实高频场景，是否与核心功能或其他插件重复。
- 同步解决多设备一致，备份解决误删和历史恢复，两者不能混为一谈。
- 凭证、Token、账号配置是否被版本控制排除；不得读取或展示凭证值。
- 插件升级、批量改名和自动化变更前是否有可恢复版本。
- Canvas、AI、PDF、表格、模板等能力只按真实使用场景评价，不按插件清单打勾。

## 十一、报告规则

报告先使用知识库自己的目录名和文件名，再说明它们“可能承担什么功能”。不要用模板标签替代实际对象。

推荐顺序：

1. 总体判断；
2. 识别到的功能板块：实际路径、可能功能、证据、置信度；
3. 最影响使用的问题，按真实影响排序；
4. 已具备但没有发挥作用的能力；
5. 低成本改进动作；
6. 功能待确认或需要用户判断的板块；
7. 应用层与文件层的验证边界。

不得：

- 把 Raw、Wiki、Projects、Outputs、GAP 等分析词直接当作用户必须采用的目录；
- 因目录名不同扣分；
- 把所有发现强行塞进模板分类；
- 仅凭名称判断功能；
- 把候选映射写成确认事实；
- 为了结构整齐而提出大规模迁移。
